# 21 — Recruiting as Code

## Goal

Specify configuration as code: an ATS whose configuration can be pushed from git, rolled back from the CLI, and audited in a compliance review.

Until now no research doc defined the file format, the plan and apply flow, or what rollback means. This doc does. It builds on the config revisions in [`data-model.md`](./data-model.md), the tables in [`db/structure.sql`](../db/structure.sql) and the config endpoints in [`api-strategy.md`](./api-strategy.md).

## The idea in one paragraph

An organization's configuration (pipelines, custom fields, roles, reasons, templates, sequences, automations, webhooks) lives in Big Buck as a numbered history of **config revisions**. Engineers and recruiting ops can pull that configuration into a folder of YAML files, change it in a pull request, see a **plan** that says exactly what will change and which live applications it touches, and **apply** it. Recruiters keep editing in the UI; every UI edit is a revision too, so there is one history whichever surface made the change. Rollback applies an earlier revision as a new one.

## Configuration versus data

Only configuration is code. Records stay in the database and are changed through the API.

| In scope (configuration) | Out of scope (data and secrets) |
|---|---|
| Pipeline templates: stages, order, types, guards, transitions, and the interviews inside each stage | People, applications, notes, scorecards, offers |
| Scorecard templates (rubrics) | **Job pipelines and their one-off edits** (job data, see [`job-pipelines.md`](./job-pipelines.md)) |
| Custom field groups, fields and visibility rules | Projects and their members, sequence enrollments |
| Dimensions (department, discipline, level…), and their values when `valuesSource: config` | Dimension values owned by the HRIS or edited in the UI |
| Roles and their permissions | Users and memberships (SCIM and the UI handle these) |
| Rejection, withdrawal and archive reasons | Integration credentials, OAuth tokens |
| Sources taxonomy | Webhook signing secrets |
| Organization variables | Documents and files |
| Message templates, in every language (`kind: MessageTemplate`, [`candidate-communications.md`](./candidate-communications.md#templates)) | Audit and history |
| Sequences (steps and timing, not enrollments) | Offers and their versions, approval requests |
| Automations | Interviews, calendar events, scheduling links |
| Webhook endpoints (URL and events, not secrets) | Consents, notice receipts, data requests |
| Offer templates and offer fields (`kind: OfferTemplate`), approval policies (`kind: ApprovalPolicy`), [`offers.md`](./offers.md) | Calendar connections and their credentials |
| Interviewer pools and scheduling defaults (reminders, search window), [`scheduling.md`](./scheduling.md) | Interviewer profiles (each person's working hours and limits) |
| Compliance policies, notices and consent purposes (`kind: CompliancePolicy`, `kind: Notice`), [`consent-and-compliance.md`](./consent-and-compliance.md) | |

## Principles

1. **The server holds the truth.** Config revisions in Big Buck are the canonical history. Files are a view of it. This is why UI edits and file applies can coexist.
2. **Keys, not ids.** Files refer to everything by stable `key` (`engineering-hiring`, `recruiter-screen`). The same files apply cleanly to a sandbox organization and to production.
3. **Plan before apply.** A plan shows every change and its effect on live data before anything happens.
4. **Atomic and locked.** An apply either fully succeeds or changes nothing, and it fails if someone changed the configuration since the plan was made.
5. **History only moves forward.** Rollback creates a new revision; it never rewrites history.
6. **Recruiters never need git.** The UI stays a first-class editor. Organizations that want git as the only path can turn on repository lock.
7. **No secrets in files.** Secrets are generated by Big Buck or referenced by name.

## Built in M3 (2026-10-25)

Phase 1 is built: the kinds Pipeline, ScorecardTemplate, Dimension, CustomFieldGroup (with nested fields), CustomField and ReasonSet; `pull`, `validate`, `plan`, `apply`, `history`, `diff` and `rollback`; and revisions for UI edits. Details settled while building:

- **Which kinds a folder manages.** A kind is managed when the folder holds at least one file of it, or when `bigbuck.yaml` lists it under `spec.manage`. For managed kinds the folder is the full desired state, and a missing object is archived. Other kinds are left alone, so a folder of pipelines never touches custom fields. Fields and field groups are managed together.
- **Stale files.** `pull` writes `.bigbuck-state.json` with the revision it pulled. A plan built from files pulled before a UI or API edit to an object it also changes lists that object under `stale_objects`, and apply is refused with `config_files_stale` until the folder is pulled again. Earlier applies of files never make files stale.
- **Stages holding open applications.** A template change that strands applications without a `stageMap` holds the affected jobs for review (`needs_review`) instead of refusing the whole apply. The plan's impact lists each held job and why.
- **Dimension values.** Removing a value still in use is refused unless the Dimension's plan-only `reassign: { old: new }` says where its records go.
- **Conditions.** Stage guards accept a structured `when` rule (see [`build-plan.md`](./build-plan.md#if-rules)) with an optional `message`, alongside `fields_present`. The rule environment exposes `person`, `subject` (the application or project member) and `owner` (its job or project).
- **Not yet in files:** dimension attributes and organization variables (with the phase 2 kinds).

## File format

Every file uses the same envelope: `apiVersion`, `kind`, `metadata` (`key`, `name`, optional `description`), and `spec`. A published JSON Schema per kind gives editors autocomplete and inline errors.

**Conditions and templates** (revised 2026-10-25). Every condition (stage guards, approval and compliance `when`, automation `where`, approval step `when`) is a **closed structured YAML rule** — fixed operators, fixed field paths, type-checked against the fields and dimension attributes it reads during `validate`. No CEL and no eval'd code in v1 ([`decisions.md`](./decisions.md#decided-2026-10-25), [`build-plan.md`](./build-plan.md#if-rules)). Message bodies and offer letters use Liquid syntax; `.docx` letters are rendered with a template library behind the letter interface. No other rule or template syntax exists.

### Pipeline template

A template is what new jobs start from. Each job then gets its own pipeline and can be edited one-off without touching the template ([`job-pipelines.md`](./job-pipelines.md)). Interviews are defined inside the stage they happen in.

```yaml
# yaml-language-server: $schema=https://api.<domain>/v1/config/schema/pipeline.json
apiVersion: bigbuck/v1
kind: Pipeline
metadata:
  key: engineering-hiring
  name: Engineering hiring
spec:
  object: application
  isDefault: false                   # one template per object type is the org default
  defaultFor:
    discipline: [engineering]        # jobs tagged Engineering (or below) start here
  transitions: forward_and_back      # forward_only | forward_and_back | any
  stages:
    - key: review
      name: Application review
      type: review
    - key: recruiter-screen
      name: Recruiter screen
      type: screen
      interviews:
        - key: recruiter-call
          name: Recruiter call
          format: phone
          duration: 30
          interviewers: { roles: [recruiter], count: 1 }
          scorecard: recruiter-screen
          scheduling: self_schedule  # self_schedule | availability_request | coordinator | manual | none
          required: true
    - key: onsite
      name: Onsite
      type: interview
      lock: structure                # jobs keep this stage; interviews stay editable (none | structure | full)
      interviews:
        - { key: coding, name: Coding, format: video, duration: 60, scorecard: coding, required: true }
        - { key: system-design, name: System design, format: video, duration: 60, scorecard: system-design, required: true }
        - { key: values, name: Values, format: video, duration: 45, scorecard: values, required: true }
      exit:
        require:
          - scorecards_submitted: { interviews: required }
    - key: offer
      name: Offer
      type: offer
      entry:
        require:
          - approval: { role: hiring-manager }
  migration:
    stageMap:
      phone-screen: recruiter-screen # where applications go when a removed stage still holds them
```

An interview run by a connected provider (an assessment platform, an async video tool, an agent) is an interview like any other:

```yaml
    - key: skills-test
      name: Skills assessment
      type: assessment
      interviews:
        - key: coding-test
          name: Coding test
          format: external
          duration: 60
          provider: { key: assessment-vendor, test: backend-fundamentals }
          scheduling: none           # the provider sends its own link, after consent checks
          scorecard: coding-test
          required: true
```

## The workflow

```text
bigbuck config init --preset recruiting-team   # new folder; roles from a governance preset
bigbuck config pull        # write the organization's current configuration into ./bigbuck
bigbuck config validate    # offline: schema, references between files, naming rules
bigbuck config plan        # server-side diff against the head revision, with impact
bigbuck config apply       # apply the plan if the head has not moved
bigbuck config history     # list revisions: number, source, author, time, commit
bigbuck config diff 41 44  # compare any two revisions
bigbuck config rollback --to 41
```

Every command takes `--org` (an alias from `bigbuck.yaml` or an organization id) and `--json`.

### Plan

`plan` uploads the compiled files to `POST /config/plans`. The server validates them, diffs them against the head revision and computes the effect on live data. The plan is stored, bound to the head revision it was computed against, and identified by a hash.

Example output (numbers are illustrative):

```text
$ bigbuck config plan --org production
Comparing ./bigbuck with acme, head revision 41 (2026-10-20, maria@acme.com, ui)

pipeline template engineering-hiring: version 3 → 4
  + stage skills-test (assessment), after review, with interview coding-test
  + interview bar-raiser in onsite
  - stage phone-screen
      12 open applications in 3 jobs are in this stage
      → will move to recruiter-screen (stageMap)
  jobs using this template: 40
    31 following      → update automatically
     7 customized     → their edits re-apply cleanly, update automatically
     2 customized     → conflict, stay on their current version and need review:
         Backend Engineer II: edit "add interview hiring-manager-chat to phone-screen" targets a stage this change removes
         Data Engineer II: job already added a stage with key skills-test

custom field group candidate-profile
  + field notice-period-days (number)

reason set rejection
  ~ compensation: label "Comp mismatch" → "Compensation mismatch"

Impact: 38 jobs update; 2 held for review; 12 applications move stage; scheduled interviews are not touched.
Plan pln_8ZqK2: 4 to add, 2 to change, 1 to remove. Valid while head is revision 41.
```

### Apply

`apply` sends the plan id to `POST /config/applies`. In one transaction the server:

1. locks the objects the plan changes and checks that each is still at the version the plan was computed against; otherwise it fails with `409 config_object_changed`, naming the objects (updated 2026-10-24: conflicts are per object, so a UI edit to a message template does not invalidate a plan that only changes a pipeline template)
2. writes the new `config_revisions` row with the full manifest, the plan and the git commit if one was supplied
3. writes the changes: new `pipeline_versions` and their `pipeline_stages`, field definitions, roles, reasons, templates, sequences, automations, webhook endpoints
4. emits a `config.applied` event

After the revision commits, a tracked job re-resolves every job pipeline built from a changed template: following jobs and cleanly merging customized jobs get a new version; conflicting jobs are flagged `needs_review` and keep their current version. Applications in removed stages move by `stageMap`, each with a stage transition (`reason = pipeline_upgrade`, `source_surface = config`). The job is idempotent and resumable, and its progress shows in `bigbuck config history`. Closed and archived jobs are never touched.

### Guardrails on destructive changes

| Change | Behavior |
|---|---|
| Remove a stage that holds open applications in any job | Refused unless `stageMap` covers it |
| Remove, retype or move a locked stage | Refused for jobs at `lock: structure` and `full`; only the template can change it. At `structure`, jobs can still change the stage's interviews with `job.pipeline.edit_locked_interviews` |
| Remove a dimension value that records use | Archived, with `reassignTo` required for open jobs |
| Remove a custom field that has values | Field is archived, not deleted; values are kept and hidden |
| Remove a role that has members | Refused unless the plan reassigns them |
| Remove a reason used by past records | Archived; history keeps the key and label |
| Change a field's type | Refused; add a new field and migrate values through the API |
| Remove a webhook endpoint | Allowed; pending deliveries are cancelled and listed in the plan |

Archived items come back if a later revision restores them, which is what makes rollback safe.

## UI edits and drift

- An edit in the UI creates a revision with `source = ui`, exactly as an apply does.
- A plan made from a stale folder says so: `head is revision 43; your files are based on 41; 2 changes made in the UI by maria@acme.com`. If those changes touch objects the plan also changes, the apply is refused until the folder is refreshed with `bigbuck config pull`, which writes the UI changes into the files so they can be committed. Changes to other objects do not block the apply; they are pulled on the next `pull`.
- **Repository lock** (optional, per organization): configuration screens in the UI become read-only and show "Managed in github.com/acme/recruiting-config". Only applies from an approved credential can change configuration. Larger customers will want this for change control. The lock covers organization configuration only: recruiters can still edit a job's own pipeline, because that is job data ([`job-pipelines.md`](./job-pipelines.md)). It can be limited to some kinds, for example roles and permissions only. Under the hood it is the strictest permission posture ([`permissions.md`](./permissions.md#every-setting-is-a-permission)): for each locked kind, the edit permission is withdrawn from every human role and held only by the repository's apply credential. Turning it on or off needs `config.lock`, which no preset grants beyond admins. For emergencies, see [break glass](#emergency-override-break-glass).

## Emergency override (break glass)

Repository lock has one failure mode: when CI is broken, GitHub is down, or the only person who can merge is on a plane, a locked organization cannot change its configuration at all, even in an emergency. Examples: a compliance step must be added to every job before Monday, an automation is emailing candidates the wrong thing, or a scorecard leaks information it should not.

Break glass is a short, loud, fully recorded exception.

**Opening it**
- Only users holding `config.break_glass` can open it. That is admins-only in every preset, and an organization can narrow it to named people.
- The admin gives a **reason** (required), the **duration** (default 60 minutes, maximum 4 hours) and which locked kinds it covers (default: all of them).
- Optionally (`breakGlass.requireSecondAdmin: true`), a second admin must approve before it opens.
- An organization has at most one open session at a time.

**While it is open**
- Only the admin who opened it can edit the covered settings in the UI. Everyone else still sees read-only screens.
- Every screen shows a banner with who opened it, why, and when it closes.
- Each edit is an ordinary config revision (`source = ui`) tagged with the session, so it appears in history, plans and audit like any other change.
- Break glass cannot be used to turn off repository lock, change who holds `config.break_glass`, or extend its own time limit. Extending means closing it and opening a new session with a new reason.

**Telling people**
- All admins are emailed the moment it opens and again when it closes, with the list of changes made.
- `config.break_glass_opened`, `config.break_glass_closed` and `config.break_glass_reconciled` events go to webhooks, so a Slack or PagerDuty alert is one subscription away.

**Closing and catching the repository up**
- The session closes at its time limit or when the admin closes it, whichever comes first.
- The organization is then marked **out of sync with its repository**. Nothing gets lost or silently reverted: the repository's next `apply` is refused with `config_head_moved`, because its files no longer match the head revision ([Apply](#apply)).
- `bigbuck config pull --break-glass <session>` writes the emergency changes into the files. Someone commits them through a normal pull request, and the session is marked **reconciled** with that commit.
- The out-of-sync warning stays on the dashboard, and in `bigbuck config history`, until reconciliation. Once a GitHub connection exists (phase 3), Big Buck can open that pull request itself.

| Command | Endpoint |
|---|---|
| `bigbuck config break-glass open --reason "…" --for 1h [--kinds pipelines,automations]` | `POST /config/break-glass` |
| `bigbuck config break-glass close` | `POST /config/break-glass/{id}/close` |
| `bigbuck config break-glass list` | `GET /config/break-glass` |

## Rollback

`bigbuck config rollback --to 41` takes revision 41's manifest as the desired state, plans it against the head and applies it as a new revision (say 44) after the same review.

Rollback restores configuration, not history. Applications stay where they are; a rolled-back pipeline becomes a new version whose definition matches the old one, and open applications follow the same migration rules as any other change. Archived fields and reasons come back with their values.

## CI integration

Plan on every pull request, apply on merge, and apply only the plan that was reviewed:

- the plan job registers its plan against the pull request's head commit (`--commit`)
- the apply job asks for the plan registered for that commit (`--plan-for-commit`); the server applies it only if the merged files compile to the same manifest hash **and** the configuration head has not moved since the plan
- if either check fails (someone edited in the UI, or `main` changed underneath), the deploy stops and asks for a fresh plan instead of overwriting anything

```yaml
# .github/workflows/bigbuck-config.yml
name: Big Buck config
on:
  pull_request:
    types: [opened, synchronize, reopened, closed]
    paths: ["bigbuck/**"]

permissions:
  contents: read
  pull-requests: write

jobs:
  plan:
    if: github.event.action != 'closed'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 10.34.5
      - run: pnpm add --global @bigbuck/cli
      - run: bigbuck config validate
      - run: >
          bigbuck config plan --org production
          --commit ${{ github.event.pull_request.head.sha }}
          --format markdown --out plan.md
        env:
          BIGBUCK_API_KEY: ${{ secrets.BIGBUCK_PLAN_KEY }}
      - run: gh pr comment ${{ github.event.pull_request.number }} --body-file plan.md
        env:
          GH_TOKEN: ${{ github.token }}

  apply:
    if: github.event.action == 'closed' && github.event.pull_request.merged
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.merge_commit_sha }}
      - uses: pnpm/action-setup@v4
        with:
          version: 10.34.5
      - run: pnpm add --global @bigbuck/cli
      - run: >
          bigbuck config apply --org production
          --plan-for-commit ${{ github.event.pull_request.head.sha }}
          --commit ${{ github.event.pull_request.merge_commit_sha }}
        env:
          BIGBUCK_API_KEY: ${{ secrets.BIGBUCK_APPLY_KEY }}
```

The plan key has only `config:plan`; the apply key has `config:apply` and lives in a protected GitHub environment, so a required reviewer can gate production. Requiring branches to be up to date before merging keeps the merged files identical to the planned ones. A later phase replaces stored keys with OIDC token exchange from GitHub Actions.

## Validation

`bigbuck config validate` runs offline and checks:

- every document against its kind's JSON Schema
- references between files: stage keys in automations, templates in sequences, roles in visibility rules, scorecard templates in stage interviews, dimension values in `defaultFor`, variables in message templates
- no two templates claim the same dimension value in `defaultFor`, and exactly one is `isDefault` per object type
- keys are unique per kind and use lowercase letters, digits and hyphens
- no secret-looking values in any field (a pattern scan, failing the build)

The server repeats all of this during `plan` and adds checks that need live data, such as stages that still hold open applications.

## Phasing

**Phase 1**
- pipeline templates (with interviews in stages), scorecard templates, dimensions, custom fields and reason sets as files
- per-job pipeline edits in the UI and API
- `pull`, `validate`, `plan`, `apply`, `history`, `diff`, `rollback` in the CLI
- UI edits create revisions

**Phase 2 (still v1: enterprise change control)**
- roles, message templates, sequences, automations, webhook endpoints, organization variables, offer templates, approval and compliance policies
- the GitHub Action and pull-request plan comments
- repository lock, with the break-glass override

**Phase 3**
- promotion between organizations (`plan --org production` from files proven on sandbox already works; add a guided `promote` command)
- approval required for production applies, using the existing `approvals` table
- OIDC from CI instead of stored keys
- Big Buck opens the reconciliation pull request after a break-glass session itself, through a GitHub connection

## Open questions

1. ~~Per-job variations~~ Decided 2026-10-24: every job gets its own pipeline built from a template plus one-off edits; see [`job-pipelines.md`](./job-pipelines.md).
2. **YAML only?** Some teams will want computed configuration (TypeScript, like Pulumi). Recommendation: YAML in v1; the manifest format is JSON underneath, so other front ends can come later.
3. **Repository lock default.** Lock applies to organization configuration only (templates, fields, roles, dimensions defined in files); it never blocks recruiters from editing a job's own pipeline. Recommendation: off by default for every plan, opt-in per organization, with the option to lock only some kinds (for example roles and permissions) and leave the rest editable in the UI.
4. ~~Departments and locations~~ Decided 2026-10-24: they become dimensions, and each dimension chooses where its values come from (`config`, `ui` or `hris`); see [`org-structure.md`](./org-structure.md).
